agyr vs proxy routers (e.g. 9router): two ways to rotate Antigravity CLI accounts

When using Google Antigravity CLI (agy), long coding sessions often exhaust rolling 5-hour or weekly quota limits. Developers addressing HTTP 429 quota exhaustion generally choose between two patterns: local CLI token swappers like agyr, and proxy routers such as 9router. Both designs aim to maintain continuous AI coding assistance, but operate at different architectural layers. This comparison reviews how both approaches handle execution, credential storage, protocol updates, and session recovery.

Architectural Overview: CLI Swapping vs Proxy Routing

A CLI swapper like agyr works directly at the process invocation layer. It is a lightweight Bash utility that manages OAuth tokens on the local filesystem. When running agyr or automated workflows with agy-run, the utility swaps active credentials and executes the official agy binary directly on the local system. Requests travel straight between Google and the CLI binary without a proxy in the path.

In contrast, proxy router systems operate as background network daemons. Instead of delegating directly to the official CLI binary on the host machine, client tools configure an HTTP or SOCKS proxy endpoint. The proxy daemon intercepts outbound network requests, injects credentials from an account pool, and forwards calls to Google. This introduces an extra intermediary layer between the client environment and remote services.

Execution Mechanics and Upstream Compatibility

Direct CLI execution preserves authentic client TLS handshakes and HTTP/2 network characteristics. Tokens reside locally in ~/.gemini/antigravity-cli/accounts/ under chmod 600 on Linux or in Windows Credential Manager under gemini:antigravity. Because agyr invokes the official binary directly, authentication uses standard operating system file permissions and keyring storage without routing traffic through a local daemon.

Upstream updates also follow standard CLI behavior. Because agyr wraps the installed agy binary directly, upstream updates released by Google become active as soon as you update agy on your system. In contrast, proxy-based architectures that translate or parse streaming protocols may require software updates whenever upstream protocol structures or API signatures change.

429 Failover and Session Continuation

Continuous workflows require reliable failover when encountering HTTP 429 quota limits. The agy-run utility monitors execution in real time. When receiving a 429 status, it stops the process, applies a cooldown timer, rotates to the next ready account, and resumes with --conversation <id>.

Because conversation context is stored locally by the Antigravity CLI, task execution resumes without re-reading files or repeating earlier prompts. Proxy-based setups can sometimes drop connections mid-stream or require replaying prompts depending on their connection handling.

Trade-offs Between CLI Swappers and Proxy Routers

Choosing between a native CLI swapper and a proxy router depends on workflow scope and tool variety:

A proxy router architecture offers multi-tool flexibility. By exposing a central HTTP or SOCKS endpoint, a single proxy daemon can route traffic for multiple distinct editors, scripts, or custom API tools. If an environment requires multiplexing across diverse developer tools through one shared network port, a proxy router provides that centralized gateway.

Conversely, agyr is dedicated specifically to wrapping the official Antigravity CLI binary. It requires no background daemon, consumes zero memory when idle, and avoids network translation layers. For developers focused on the official agy tool, installation requires only standard commands: 

curl -fsSL https://agyr.luongtrz.id.vn/install.sh | bash
agyr list
agy-run --add-dir . --prompt "Refactor database queries and add indexes"
