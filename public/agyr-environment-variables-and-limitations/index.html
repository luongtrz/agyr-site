agyr environment variables and known limitations

The agyr tool suite rotates multiple Google accounts for Google Antigravity CLI (agy) and monitors account quotas in real time. This guide documents configuration environment variables, timestamp formatting, time zone handling, and known limitations across agyr, agy-run, and agy-task. Install agyr using the unified installer: 

curl -fsSL https://agyr.luongtrz.id.vn/install.sh | bash

Environment Variables Reference

The agyr commands read configuration options through environment variables to manage data directories, binary selection, time zones, output styling, and runner timeouts. The table below lists every environment variable documented in the official reference specification, including its default value and purpose.

Variable Default Purpose
AGY_HOME ~/.gemini/antigravity-cli agy data directory
AGY_BIN agy agy binary
AGY_TZ UTC-7 (UTC+7) Time zone for displayed timestamps
AGY_NOW current epoch Test hook: override current time
AGYR_COLOR auto auto (colored on TTY when NO_COLOR is unset), always, or never
AGYR_TEST_TIMEOUT 120 Per-account timeout in seconds for agyr test
AGY_RUN_MAX_SWITCH 10 Maximum account switches per agy-run
AGY_RUN_POLL 1 Poll interval in seconds for agy-run

In daily operation, AGY_HOME is the agy data directory (default ~/.gemini/antigravity-cli), and AGY_BIN specifies the agy binary. AGYR_COLOR controls terminal coloring (auto: colored on a TTY when NO_COLOR is unset, always, or never).

For headless automation, AGY_RUN_POLL sets the poll interval (default 1s) and AGY_RUN_MAX_SWITCH caps failover switches (default 10, exiting with code 6). AGYR_TEST_TIMEOUT limits individual agyr test probes to 120 seconds, and AGY_NOW is a test hook for overriding epoch time in test suites.

Time Zone Behavior and Timestamp Formatting

All timestamps displayed by agyr default to UTC+7 in dd/mm/yyyy hh:mm AM|PM format (for example, 01/10/2026 07:14 PM). This consistent display formatting applies uniformly across quota inspection tables in agyr list and connection probe summaries in agyr test, regardless of the host machine's system locale or time zone.

Override the display time zone with the AGY_TZ environment variable (for example, AGY_TZ=UTC). In standard POSIX TZ syntax, offset signs are inverted: a positive offset east of UTC uses a minus sign, making UTC-7 the default representation for UTC+7.

Known Limitations of agyr

The official technical reference lists the following known limitations for agyr and its headless runner agy-run:

  • Running agy processes keep their initial token in memory; agy-run always kills and resumes the conversation rather than hot-swapping tokens.
  • agy-run only triggers a quota switch on plain-text error: Individual quota reached … or AGY_ERROR: … RESOURCE_EXHAUSTED (code 429) lines. When a conversation that previously hit 429 is resumed, agy still echoes the old quota error inside the final {"event":"result"} JSON (status: "ERROR", error: "Individual quota reached …") even when the resumed turn completed normally; agy-run ignores JSON lines so it does not switch accounts falsely, and returns exit 0 when .result.response is non-empty (or exit 1 if response is empty).
  • 503 No capacity errors are not switched automatically by agy-run; follow skills/agy/references/503-fallback.md (gemini-3.8-flash-medium, then gemini-3.8-flash-low).
  • Parallel agy-run processes share one pool best-effort: parallel agy-run processes still share one live token file, so if process B switches the active token between process A's agyr use X and agy reading the token file, a later cooldown in process A may be recorded against the wrong account name until the next agyr list reconciles the quota table.
  • On Windows, the wincred backend is tested against test/fake-cred; because each Credential Manager read/write spawns PowerShell (~1 s), agyr list measures accounts sequentially rather than in parallel, and you should not sign in manually while agyr list or agyr use is running.

Where agyr Limitations Matter in Practice

These technical limitations influence daily development workflows, automated scripts, and multi-process workloads:

Because running agy processes keep tokens in memory, credentials cannot update inside an open session. Developers must exit agy before running agyr rotate and continuing with agyr -c. In automation, agy-run terminates the process upon 429 exhaustion and resumes with --conversation <id>.

Because a resumed conversation can still echo the earlier 429 in the final JSON event, status: "ERROR" alone does not mean the resumed turn failed. Resumed turns that finish normally can still contain the prior quota error in the result event; agy-run ignores JSON lines during switching and exits with code 0 when .result.response is non-empty.

agy-run does not switch accounts automatically on 503 No capacity errors; the reference points to skills/agy/references/503-fallback.md, which uses the gemini-3.8-flash-medium model first and then gemini-3.8-flash-low.

When running parallel agy-run tasks, processes share one live token file. A switch by another process can cause a subsequent cooldown to be recorded against the wrong account until the next agyr list reconciles state.

On Windows, Credential Manager access overhead requires agyr list to measure accounts sequentially rather than in parallel (~10–20 seconds on Linux). Do not sign in manually while agyr list or agyr use is running.

Known Limitations of agy-task

When AI orchestrators delegate coding tasks through agy-task, tasks execute inside dedicated Git worktrees. The official technical reference identifies two specific limitations:

  • The worktree starts from --base and does not inherit uncommitted changes from the main checkout.
  • Scope and forbidden-file checks only see files reported by git status / git diff (gitignored files are invisible to git).

In practice, worktrees branch from --base (default HEAD), so uncommitted changes in the main checkout are not present in the task. Work must be committed or handled before running agy-task. Furthermore, because Git ignores paths in .gitignore, modifications to gitignored files are invisible to scope checks.
